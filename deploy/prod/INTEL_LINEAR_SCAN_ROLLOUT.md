# Intel CPU linear-scan rollout

Preparation only. Daniel Kalas owns stack review. Do not merge these values, sync Argo, or deploy until the release and live qualification gates below are complete and the production rollout is approved.

## Configuration

One existing deployment per party moves from ARM `r8g.24xlarge` to on-demand Intel `r8i.24xlarge`, selected and tolerated by `application=cpu-linear-scan`. Requests and limits remain 92 CPU / 700Gi. The dedicated 96-CPU NodePool has nominal capacity for one such host per party; Karpenter limits are eventually consistent, not a strict node-count guarantee. Creating the pool alone does not create a host.

Batch maximum 16, S3 importer parallelism 8, and 12 Tokio cores per NUMA node follow stage configuration `d6b8bf42c74a1650518e59cf6c6c13fb5f54e1d7`. This is configuration evidence, not qualification of the eventual production image. `numactl::init` reserves the first 12 CPU IDs on each detected NUMA node; the runtime uses 12 times the NUMA-node count. NUMA defaults on. Verify actual topology, CPU affinity and allocatable capacity with the production AMI and container before serving traffic.

`INIT_DB_SIZE=0` remains unchanged; `CLEAR_DB_BEFORE_INIT=false` prevents initialization from clearing the existing database. Production `SMPC_rerand` schema base and `_genesis_restored_v2` suffix, S3 buckets/prefix, queues, secret references, LUC and persistence settings remain unchanged. The existing 18,000,000 database capacity is retained, not introduced from the stage fixture. Check current production size and growth headroom before rollout; increase it only with a reviewed memory/capacity calculation. Do not use stage schemas, generated fixtures, exports or queue namespaces.

`Recreate` is retained. A surge pod cannot fit alongside a 92-CPU pod on a single 96-CPU pool. This deployment strategy avoids that deadlock but does not coordinate the three parties: plan a coordinated interruption and reload. The existing startup budget is approximately 75 minutes (15-minute delay plus 120 checks at 30 seconds), and shutdown grace remains 500 seconds. Validate these bounds and the 65-attempt / 3-second initial heartbeat tolerance against production load time and inter-party startup skew before activation.

## Coordinated activation and recovery

1. Record existing Argo sources/parameters, rendered values, image digests and database/control-plane frontiers. Confirm a fresh complete S3 snapshot plus PG overlay/frontier and that the reviewed rollback source can read the resulting schema and journal. An eligible ARM pool is not warm rollback capacity: empty-node consolidation can retire hosts after stopping the application. Use an approved temporary reservation or explicitly accept ARM reprovisioning delay.
2. During the approved window, pause both parent and child Argo automatic synchronization, then pause/drain the relevant ingestion path and prevent overlapping consumers. Keep queued work intact. Stop the existing CPU parties together and verify their deployment-owned pods have exited before starting replacements; `Recreate` alone does not enforce this fleet barrier.
3. Activate the reviewed Intel image/configuration on all three parties. Optional prewarming must use a temporary capacity reservation removed before the application needs the host; it must not start another queue consumer. Do not create A/B deployments.
4. Require all parties to finish loading and reach readiness without restart loops. Compare loaded counts/frontiers and actual pod image, architecture, NUMA settings and environment against the approved render. Resume ingestion progressively. Verify a fresh unique enrollment and an identical-biometric enrollment under a fresh identity rejected against that exact serial, with final and all three party results. Agree latency, backlog and error abort thresholds before the window; stop progression on disagreement, restart loops or breached thresholds. Check pending requests and unfinished modifications drain before closing the window.
5. On failure, pause ingestion and stop the replacement fleet before recovery. Restore the reviewed compatible application configuration on available capacity and repeat readiness/data checks. Keep database clearing disabled during rollback, including when restoring an older values revision that enabled it. Preserve newly accepted records; do not point at a stale schema or restore a database independently of its coordinated ingestion/control-plane state. If migrations prevent binary rollback, use the reviewed forward recovery path.
6. After acceptance, restore the recorded ingestion replicas/policies and parent/child Argo reconciliation policies. Verify that the merged production source reproduces the approved image, data sources and configuration without manual overrides.
